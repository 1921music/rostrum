# 本棚のモデルとビュー

本棚はモデルとビューに分ける。DB・同期方式はこの分離のためには変更しない。
フレームワーク、汎用MVC基盤、新しいテーブルは追加しない。

## 現在の構成

- `src/bookshelf-model.js` — `BookshelfStore`。データの取得・変更、一覧の組み立て、
  保存場所、同期、転送の受付と状態管理を担当する。DOMや画面の部品を操作しない。
- `src/bookshelf.js` — `BookshelfView` と既存アプリへの接続。
  表示、検索条件など画面内の状態、入力、確認ダイアログ、進捗表示を担当する。
  既存の楽譜表示・取り込み確認画面やクラウド接続の生成もここでモデルに渡す。
- DBワーカー、同期処理、転送キュー、保存・クラウドの各実装は既存のものを使う。
  モデルの下に汎用サービス層やリポジトリ層を追加しない。

ビューはモデルの操作を呼び、`datachange`、`statuschange`、`permissionchange` を
受けて表示を更新する。`warning` はアプリ側でトースト表示する。
ビューはDBワーカーのコマンドや転送キューのジョブを直接操作せず、モデルの状態を
書き換えない。同期の必要性はモデルが判断し、画面はその結果でボタンや件数を表示する。
手動同期と自動同期は同じモデルの同期処理を使う。

モデルは画面なしでも起動・検証できる。`BookshelfView` はコンストラクタでモデルを
受け取れる。既存の楽譜画面からの保存などは引き続き `window._bookshelf_` に接続する。

## 今後の境界

- 今の実装に必要なこと: 上記の責務分離と状態管理。既存の画面動作を維持する。
- 今考えておくこと: DBのバージョン、IDと保存パスの区別、同期の詳細をビューに
  漏らさないこと。将来の変更はこの境界の内側で扱えるようにする。
- 必要になってから考えること: 具体的なデータ移行、履歴の圧縮、検索・キャッシュの
  高度化、転送の並列化。関連付けの重複や競合の解決ルールも今回の分離では変更しない。

## 同期状態と操作可否

クラウド確認と同期実行は同じremoteInventoryを保存する。未知の変更バッチがあるかも
その観測情報に含める。syncSummaryが未送信変更・未アップロード・未ダウンロードを
集計し、モデルがその結果を画面に渡す。cloudPendingは独立して更新せず導出する。
operationBlockが操作を止める理由を返し、画面・保存先変更・同期開始・自動同期で使う。
転送キューの進捗はstatuschangeだけを通知し、一覧全体の再取得を起こさない。
