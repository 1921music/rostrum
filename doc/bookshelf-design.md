# 本棚・曲の索引・書き込みのデータ設計案

状態: 実装前の設計案。ブランチ `bookshelf` で本棚機能を実装するための出発点。
最終DDL、同期プロトコル、JSONの詳細仕様は今後決定する。

## 目的と前提

- 多数のPDF・MSCZを登録し、本棚で整理する。
- 曲名・作曲者・タグから、登録済みの楽譜全体を検索する。
- 曲集PDFは分割せず、PDF標準のしおりから曲の索引を作り、検索結果から対象位置を開く。
- 単曲ファイルも曲の索引を持つ。同じ作品の別版・別編曲は別の索引として扱う。
- 本棚はファイルの整理、playlistは曲の演奏・練習順の管理とし、別機能にする。
- 通常の書き込みはDBに保存し、表示時に楽譜へ重ねる。ファイルへの反映・書き出しは明示操作で行う。
- 同期の通信機能は後から実装できるが、端末間同期は必須要件として最初から考慮する。

## 保存方式

本棚の正本はアプリ管理下のコピーとする。ローカルから取り込んだ楽譜は本棚の管理領域へコピーし、元の外部ファイルへの継続アクセスには依存しない。外部ファイルの変更は自動反映せず、再取り込み・差し替えとして扱う。

管理領域は共通の保存APIを通じて扱う。OPFS、ユーザーが選ぶ専用フォルダへのFile System Access API、IndexedDBなどを候補とし、環境ごとの採用方式は後で検証して決める。現在のOPFS実装は開発用の接続先であり、環境ごとの選択を確定するものではない。

本棚の処理は、相対パスで楽譜を読み書きするファイル層と、SQLiteの実行・永続化・書き出しを担当するDB層を通す。OPFSのルート取得やSQLite用VFSの選択を本棚処理へ直接埋め込まない。同じ相対パスと論理スキーマを保存先によらず使う。

ユーザーが選んだフォルダではOPFS専用SQLite VFSをそのまま使えない。DBファイルの永続化、排他制御、保存失敗時の復旧は別バックエンドとして検討する。フォルダハンドルを渡すだけでSQLiteの保存先も切り替わる設計にはしない。`file://`ではWorker・WASMの読み込み方法も検証が必要。

```text
library.sqlite
scores/<documentId>__ショパン・ワルツ曲集.pdf
scores/<documentId>__月光ソナタ.mscz
```

- SQLiteの永続化は共通APIのDB層が担当する。具体的なSQLite WASM・VFS・永続化手段は対象環境で検証して選ぶ。
- 楽譜本体はSQLiteのBLOBではなく、共通APIのファイル層で個別に保存する。IndexedDBの場合は相対パスをキーにBlobとして保持する実装も可能とする。
- 管理領域とクラウドで相対パスを共通にする。物理ファイルのパスを公開しないバックエンドでも同じ論理キーとして扱う。
- 版違いは別のdocument IDを持つため、パスに版のハッシュやdocument専用ディレクトリは設けない。
- 名前部分は取り込み時の名前を元に、禁止文字・長さを調整して固定する。表示名を変更してもパスを変更しない。
- 完全な元ファイル名はJSONに保存する。ハッシュは内容照合・重複検出・転送後の検証に使う。
- クラウド由来でも、登録後の本体はアプリ管理下で扱う。取得元の情報は出所として保存できる。
- ファイルハンドルを本棚の永続参照として保存する必要はない。

## カラムとJSONの方針

識別、関連付け、同期、ファイル取得に必要な項目は通常のカラムにする。それ以外は用途別のJSONに保存する。

曲名・作曲者などもJSONに置ける。検索が必要なスカラー値には `json_extract()` の式インデックスを追加できる。配列の別名や部分一致を扱う検索は、必要に応じて再生成可能な検索用テーブル・全文検索索引を設ける。

JSONも各項目の意味・型・既定値を定義し、任意のデータを無制限に混在させない。DBのスキーマバージョンと、必要に応じたJSON形式バージョンで移行する。

## 共通カラム

以下の共有データ用10テーブルに共通する。

| カラム | 内容 |
| --- | --- |
| `id` | 全端末共通のUUID。変更・再利用しない |
| `revision_id` | 現在の行の変更IDという案。`changes`とともに同期方式の検証後に確定 |
| `deleted_at` | 未削除はNULL。削除時も同期用の記録を残す |

`deleted_at`や記録日時だけで変更の新旧を決めない。変更の親子関係による競合検出を候補とするが、追跡情報の具体形は同期方式を検証して確定する。

以下のカラム一覧では共通カラムを省略する。IDの参照は外部キーとして定義するが、削除は原則として物理削除ではない。受信順が前後する同期データは、依存関係を確認してから適用する。

## 1. documents — 楽譜ファイル

1行は特定の内容を持つ楽譜ファイル。版テーブルは設けず、版違いも別の行に登録する。

| カラム | 内容 |
| --- | --- |
| `content_hash` | 内容ハッシュ。アルゴリズムは統一する（SHA-256を候補とする） |
| `storage_path` | 保存方式によらない論理的な相対パス。クラウドでも共通 |
| `size_bytes` | 本体のバイト数 |
| `derived_from_id` | 派生元document。なければNULL |
| `replaced_by_id` | 通常利用上の置き換え先document。なければNULL |
| `metadata_json` | 表示名、元ファイル名、形式、取り込み元、ページ数など |
| `settings_json` | 楽譜に付随するユーザー設定。検索用の索引は設けない |

```json
{
  "displayName": "ショパン・ワルツ曲集",
  "originalFilename": "ショパン・ワルツ曲集.pdf",
  "format": "pdf",
  "pageCount": 120,
  "importedAt": "2026-11-13T10:00:00Z",
  "source": { "type": "local" }
}
```

色付きしおり、移調、楽譜ごとの再生設定など、楽譜とともに共有する設定は `settings_json` に保存する。検索する情報ではないため、項目ごとのカラムや専用テーブルは設けない。端末ごとの表示・操作設定はローカル専用データとして分け、具体的な項目の区分は実装時に決める。

### 派生・置き換え・削除

これらは異なる意味を持つ。

- `derived_from_id`: このファイルを作る元になったファイル。
- `replaced_by_id`: このファイルに代わって通常使うファイル。
- `deleted_at`: ユーザーが削除した状態。

AをBで置き換える場合は、Aの `replaced_by_id = B` とする。Bを実際にAから作った場合だけ、Bの `derived_from_id = A` も設定する。関連する変更は端末内では同じトランザクションで行う。

例えば古いスキャンを別途入手した鮮明なPDFで置き換える場合、置き換え関係だけを設定し、派生関係は設定しない。

Aから別編曲Bを作って両方使う場合は、Bの `derived_from_id = A` のみ設定する。Aは置き換え済みにしない。

通常の本棚・検索では、未削除かつ `replaced_by_id IS NULL` のファイルを対象とする。旧版は履歴や明示的な表示で参照できる。循環する派生・置き換え関係は許可しない。

旧版の索引・書き込み・本棚所属・playlist参照は自動削除しない。特にplaylistの参照を無条件に新版へ付け替えない。新版への移行操作と旧版の表示方針は別途設計する。

本体の内容は登録後にその場で上書きせず、差し替え時に新しいdocumentを作る。通常の書き込み追加は本体の変更ではないため、documentを増やさない。MSCZの内容編集など、本体を変更する操作は別documentを作る対象になる。

`content_hash`は照合に使うが一意制約は必須としない。同じ内容を別の楽譜として登録することも許容する。

## 2. entries — 曲・楽章・見出しの索引

1行は「この楽譜のこの位置にある曲・楽章・見出し」。抽象的な作品そのものを表すテーブルは今は設けない。

| カラム | 内容 |
| --- | --- |
| `document_id` | 対象document |
| `parent_id` | 親entry。階層がなければNULL |
| `anchor_json` | 開く位置 |
| `metadata_json` | 曲名、作曲者、別名、作品番号、抽出元、手動修正情報など |

```json
{
  "title": "ワルツ第1番",
  "composer": "Chopin",
  "aliases": ["華麗なる大円舞曲"],
  "opus": "Op.18",
  "source": { "type": "pdf-outline" },
  "userEditedFields": ["title"]
}
```

PDFの `anchor_json` の例（ページは0始まり）:

```json
{ "type": "pdf", "pageIndex": 11, "y": 0.25 }
```

- 単曲ファイルにも原則1件作る。曲集PDFには複数作る。
- PDF標準のしおりから曲名・ジャンプ先・階層を取り込む。部・作曲者名など、曲ではない見出しも含み得るため編集可能にする。
- MSCZは内部の情報、単曲PDFはタイトル情報・ファイル名などから初期値を作る。
- entriesはタグやplaylistから参照されるユーザーデータであり、再生成して捨てられるキャッシュではない。
- 再解析では既存の索引を更新することを基本とし、ID、手動追加・修正・削除、タグやplaylistからの参照を維持する。対応を判断できない索引を自動的に削除・再作成しない。照合方法は要設計。
- 索引の初期生成・再解析も同期する変更として扱う。同じ登録済みdocumentを各端末が独立に解析して、同じ索引を別IDで重複生成しないようにする。生成・照合方法は実装時に決める。
- 親entryは同じdocumentに所属するものとし、循環を許可しない。
- 別documentへ索引を移す場合は、ページ位置などを確認する。

## 3. annotations — 書き込み

1行は独立して追加・編集・削除できる線、文字、スタンプなど。

| カラム | 内容 |
| --- | --- |
| `document_id` | 対象document |
| `anchor_json` | ページ・音楽上の位置 |
| `content_json` | 種類、座標列、文字、色、太さなど |
| `metadata_json` | その他の属性 |

`content_json` の形の例。座標や太さの単位は実装時に統一する。

```json
{
  "type": "stroke",
  "points": [[0.12, 0.30], [0.13, 0.32]],
  "color": "#e53935",
  "width": 0.002
}
```

- entryを経由せずdocumentに結び付ける。索引の削除や名前変更から独立させる。
- 通常の書き込みは自動保存する。保存失敗はユーザーにわかるようにし、保存済みとして扱わない。保存間隔や操作の確定単位は実装時に決める。
- PDFは元ページの座標系を使い、画面の倍率・回転・切り抜きに依存しない位置を保存する。
- MSCZは改ページの変化に対応するため、可能なら小節・拍・譜表などの位置を使う。具体的なアンカー形式は要検証。
- 書き込み付きファイルの書き出しは、本体とDBの書き込みから生成する。
- 書き込みを埋め込んだファイルで本棚内を置き換える場合、同じ書き込みを再度重ねないよう移行する。

## 4. tags — タグの定義

| カラム | 内容 |
| --- | --- |
| `name` | タグ名 |
| `metadata_json` | 色、説明など |

名前を変更してもタグIDは維持する。同名タグの扱い、名前の正規化、別端末で同名タグを同時作成した場合の統合規則は要設計。

## 5. document_tags — ファイルのタグ

| カラム | 内容 |
| --- | --- |
| `document_id` | 対象document |
| `tag_id` | タグ |

## 6. entry_tags — 曲のタグ

| カラム | 内容 |
| --- | --- |
| `entry_id` | 対象entry |
| `tag_id` | タグ |

タグ付与自体にもIDと削除状態を持たせ、付与・解除を独立して同期する。同じ組み合わせの有効な重複は画面上でまとめる。並行した追加・解除をどう統合するかは同期規則として決定する。

曲のタグ検索では、直接付いたタグと所属documentのタグの両方を参照する。タグを各entryへコピーしない。画面では直接のタグと継承したタグを区別する。「いずれか」「すべて」の両条件を想定する。

## 7. bookshelves — 本棚

| カラム | 内容 |
| --- | --- |
| `metadata_json` | 名前、説明、表示方法など |

本棚はファイルを整理する機能。「全楽譜」はdocumentsの一覧であり、特別な本棚レコードを必要としない。初期設計では棚の階層は設けない。

## 8. bookshelf_documents — 本棚への所属

| カラム | 内容 |
| --- | --- |
| `bookshelf_id` | 本棚 |
| `document_id` | ファイル |
| `order_key` | 手動の並び順 |
| `metadata_json` | 所属ごとの追加情報 |

同じdocumentは複数の棚に所属できる。同じ棚内の有効な重複登録は原則不要。本棚から外してもdocumentは削除しない。

## 9. playlists — 曲リスト

| カラム | 内容 |
| --- | --- |
| `metadata_json` | 名前、説明など |

演奏・練習する曲を順番に並べる機能。本棚とは別機能・別テーブルとする。

## 10. playlist_items — playlistの項目

| カラム | 内容 |
| --- | --- |
| `playlist_id` | playlist |
| `entry_id` | 曲の索引 |
| `order_key` | 並び順 |
| `metadata_json` | 演奏時のメモなど |

同じentryを複数回登録できる。それぞれ独立したIDを持ち、別々のメモや並び順を保存する。playlistから外してもentryは削除しない。

本棚・playlistの `order_key` は途中挿入できる方式を選び、並行挿入で同順位になった場合はIDなどによる決定的な順序を設ける。並べ替えの同期規則は要設計。

## 11. changes — 同期用の変更記録の候補

以下は、共有データ用10テーブルに `changes` を加える場合の構成案。全行スナップショットと親変更IDを保存する方式は候補であり、採用を確定しない。履歴容量、競合解決、複数行の適用を検証し、`revision_id`を含む具体形を決める。

この案の `changes` には共通カラムを適用せず、以下を持たせる。

| カラム | 内容 |
| --- | --- |
| `id` | 変更ID。共有データのrevision_idに対応 |
| `device_id` | 変更を作った端末 |
| `entity_type` | 対象テーブルの種類 |
| `entity_id` | 対象行のID |
| `parent_revision_ids_json` | 元になった変更ID。新規作成は空、通常更新は1個、競合解決時は複数 |
| `payload_json` | 変更後の行全体。削除状態も含む |
| `created_at` | 記録日時。競合判定には使わない |

初期実装から確保するのは、全端末共通のID、変更・削除の追跡、オフラインで行った変更を失わないこと、更新処理の共通化である。画面は直接SQLを更新せず、タグ付与・曲名変更・置き換えなどの共通処理を通す。この変更記録方式を採用する場合、本棚の変更と変更記録は同じSQLiteトランザクションで保存する。

### 同期の基本方針

- SQLiteファイル全体の転送はバックアップ・復元に使う。複数端末の編集を統合する同期は変更記録を交換する。
- 楽譜本体はファイル単位で転送する。管理領域・クラウドで共通の論理的な相対パスを使う。
- 行単位の競合検出を出発点の候補とし、JSON項目ごとの自動統合は必須にしない。
- 同じ変更IDは再適用しない。同じ行の並行変更は双方を保持し、黙って片方を捨てない。
- この案では `revision_id` は現在採用する状態を指す。未解決の並行変更はchangesに残し、競合として表示できるようにする。
- Aを別端末でそれぞれB・Cへ置き換えた場合、Aのreplaced_by_idの競合として扱う。
- 複数行の操作を部分適用しないための変更グループ・適用単位は、同期プロトコル設計時に追加する。
- 削除記録・旧変更・旧本体の回収は、オフライン端末やバックアップからの復元も考慮して決める。単なる一定日数経過では消さない。

## 端末固有データと再生成可能なデータ

以下は共有する本棚データと分離し、必要に応じてローカル専用テーブル等へ保存する。

- 端末ID、同期先ごとの受信位置、転送待ち・転送エラー。
- 各楽譜本体のダウンロード済み状態。DBに登録済みでも、本体がその端末にない状態を許容する。
- クラウド認証情報。本棚のバックアップ・変更記録へ含めない。
- 端末ごとの表示・操作設定、画面状態、検索入力など。楽譜とともに共有する設定はdocuments.settings_jsonへ保存する。
- 検索を高速化するための索引、サムネイル、解析キャッシュなど。正本から再生成可能にする。曲の索引であるentriesそのものは共有する正本に含む。

将来、必要な楽譜だけダウンロードする方式を選べるようにする。検索自体は本体未取得でもローカルの索引で行える。

## 整合性・バックアップ・実装前の確認事項

- JSONは妥当性と型を検証する。重要な参照は外部キー、必要な検索は通常／式インデックスで支える。
- storage_pathは管理領域内の相対パスに限定し、パストラバーサルを許可しない。
- SQLiteと楽譜ファイルの書き込みは同一トランザクションにならない。仮ファイル、ハッシュ検証、DB登録の順序と中断復旧を設計する。
- バックアップは整合したSQLiteの書き出しと、参照する楽譜本体から作る。書き込み中のDBを単純コピーしない。
- OPFSはブラウザ保存領域であり、サイトデータ削除や容量制限への対策として、バックアップ・復元・容量不足時の処理を用意する。
- PDFしおりと既存Rostrumのページしおりは別物として取り扱いを確認する。
- 既存のPDF内設定・書き込みをDBへ移す方法、書き込み付き書き出し、旧版への参照の表示方針を決める。
- 同期を実装する前でも、2端末相当のDBで並行編集、削除、置き換えの競合を交換して検証できる構造にする。

この文書はテーブルの責務と保存モデルを定める案であり、同期規則や復旧手順が確定済みであることを意味しない。
